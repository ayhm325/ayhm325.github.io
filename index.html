API Layer — ASP.NET Core Web API

Acts strictly as the HTTP transport and security gateway. Exposes RESTful endpoints, enforces JWT Bearer authentication, evaluates role/policy authorization, applies IP login rate limiting, and translates Application Result outcomes into standardized RFC 7807 ProblemDetails responses.

KEY ENGINEERING DECISIONS

  • Keep controllers thin: zero direct DbContext calls or embedded SQL inside controller actions.
  • Centralize failure formatting with Global Exception Handling and ProblemDetails instead of ad-hoc error strings.
  • Enforce IP-based login rate limiting (5 requests / IP / minute) returning HTTP 429 Too Many Requests.

01 // PROBLEM & DOMAIN COMPLEXITY

Why Ordinary CRUD Was Insufficient

A licensing department system cannot rely on naive table CRUD. Every operation is governed by strict state-machine invariants: a citizen cannot hold two active applications for the same license class; practical driving tests cannot be scheduled before passing vision and written tests; and a detained or expired license cannot be renewed until blocks are resolved.

  • State Integrity: Multi-step workflows (Application → Vision Test → Theory Test → Practical Test → Driver Creation → License Issuance) require atomic state transitions.
  • Decoupled Client-Server Contract: The WPF desktop presentation client communicates through DVLD.Contracts and REST APIs rather than coupling UI views directly to SQL Server.
02 // ARCHITECTURAL TRADE-OFFS & SOLUTIONS

Engineering Decisions Under the Hood

  • Shared Scoped DbContext & Unit of Work: When issuing or replacing a license, multiple repositories update application status, license records, and audit state. Coordinating them via a scoped Unit of Work with explicit Serializable transactions prevents partial writes and concurrency anomalies.
  • Result Pattern + RFC 7807 ProblemDetails: Business rule violations (e.g., active detention or unpassed prerequisites) are modeled explicitly via Result<T> and mapped deterministically to HTTP status codes, keeping exception handling reserved for unexpected infrastructure faults.

05 // ENGINEERING PHILOSOPHY PRINCIPLES & BACKGROUND

HOW I APPROACH SOFTWARE ENGINEERING

Code is read and maintained far more often than it is written. My focus is on building backend systems that remain understandable, testable, and resilient as requirements evolve.

PRINCIPLE // 01

Strict Separation of Concerns

Controllers handle HTTP transport; Application services orchestrate business use cases; Domain models hold core invariants; Infrastructure manages EF Core and SQL Server. Mixing these responsibilities creates fragile software—keeping them distinct makes every layer easier to reason about and test.

PRINCIPLE // 02

Correctness & Explicit Transactions

Business workflows rarely touch a single table in isolation. By making transaction boundaries explicit through a shared scoped Unit of Work and enforcing constraints in SQL Server, data remains consistent even when concurrent requests or unexpected failures occur.

PRINCIPLE // 03

Predictable Error Semantics

Expected domain failures (invalid state transitions, duplicate applications, rate-limit thresholds) should be represented explicitly via typed Result objects and mapped to RFC 7807 ProblemDetails—never hidden behind silent nulls or unhandled 500 stack traces.

PRINCIPLE // 04

Verification as a First-Class Citizen

Architecture is only as reliable as its verification suite. Designing with Dependency Injection and clean interfaces enables fast unit tests with Moq alongside realistic API and database integration tests with xUnit.
